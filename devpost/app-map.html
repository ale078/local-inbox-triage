App Map — Ofertas vs CV

La idea es convertir un digest de Gmail en una lista de ofertas con match contra tu CV, sin leer cada correo ni cada anuncio a mano.

Visión general

La app local corre en Python con FastAPI y sirve una interfaz web. El flujo principal es: subir CV → elegir etiqueta de Gmail → leer esos mails → extraer ofertas → evaluar afinidad con Gemini → mostrar tarjetas con porcentaje, veredicto y enlace.

Ruta de referencia

  1. Entrada main.py sirve la app web y expone GET /api/cv/status y POST /api/cv/upload.
  2. Procesado services/pdf_service.py guarda data/cv.pdf y extrae texto para comparar contra las ofertas.
  3. Extracción services/gmail_service.py y services/parser_service.py buscan enlaces y títulos dentro de los digest de Gmail.
  4. Evaluación services/gemini_service.py envía cada oferta contra el CV, devuelve porcentaje, veredicto y sugerencia.
  5. Resultado static/index.html y static/app.js renderizan tarjetas y permiten abrir cada oferta directa.

“To change this, start here”

Quiero cambiar la lógica de match

Empezá por services/gemini_service.py: ahí está el prompt y la respuesta estructurada. Cambiá el texto del prompt, el esquema de salida o el filtro de score antes de tocar la UI.

Quiero cambiar cómo se muestran las ofertas

Mirá static/app.js y su función renderJobCards. La visualización está separada de la lógica de backend y es el punto más seguro para ajustar badges, textos o columnas.

Quiero cambiar la forma de cargar el CV

Verificá main.py para la ruta de upload y services/pdf_service.py para el almacenamiento en disco. Si querés cambiar qué archivo guardan o el nombre del archivo, ese es el lugar.

Practice to reuse

La práctica útil aquí fue definir un kernel observable y luego verificarlo paso a paso: un CV cargado, una etiqueta en Gmail, una oferta extraída y una evaluación legible. La documentación en devpost/scope.md y devpost/prd.md hizo explícita la frontera del POC, y el chequeo en main.py + static/app.js mostró si el comportamiento general seguía encajando.

El mismo patrón funciona en otros proyectos: elegir el “hecho observable” más valioso, probarlo en la menor capa posible, y mantener un mapa claro de entrada → lógica → salida.

Cómo reproducirlo

Desde la raíz del proyecto:

python -m uvicorn main:app --reload --port 8000

Luego abrí http://localhost:8000 en el navegador. La app sigue siendo una caché local y no requiere despliegue para mostrar el POC.

Este mapa es una instantánea del código y puede quedar atrás si cambian las rutas o la lógica; se mantiene claro y útil sin depender de red ni de servicios externos.
